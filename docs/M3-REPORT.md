# M3 결과: OpenAI 연결과 화별 사실 추출

- 날짜: 2026-10-25
- 계획: [`M3-PLAN.md`](M3-PLAN.md)
- PR: #25 (AI 규칙 core), #26 (키 저장·OpenAI 연결), #27 (결과 저장소·분석 실행), #28 (설정·분석 버튼·사실 패널), #29 (두 화씩 동시 분석·호출 시간 기록)

## 결론

**M3 성공 기준을 모두 충족했다.** 작가가 버튼을 누르면 화마다 인물과 사실을 원문 인용과 함께 뽑아 `.loreweave/ai.db`에 저장한다. 사실의 인용을 누르면 본문의 그 문장으로 이동한다. 키가 없어도 M1·M2 기능은 그대로 동작한다.

| 기준 (M3-PLAN 5절) | 결과 | 확인 방법 |
|---|---|---|
| 키 보안 | 디스크에 평문 키 없음. renderer는 저장 여부만 앎 | E2E |
| AI 없이 동작 | 키 없이 M1·M2 E2E 모두 통과 | E2E |
| 인용문 존재 검사 | 본문에 없는 인용을 가진 사실은 저장하지 않음 | 단위 테스트 (가짜 응답) |
| 실제 추출: 인용 보존 ≥ 90% | 1차 99.5% (219개 중 218개), 2차 99.1% (229개 중 227개) | 실제 실행 2회 |
| 실제 추출: 화당 ≤ $0.005 | 최대 $0.0011 (15화 합계 1차 $0.0119, 2차 $0.0102) | 실제 실행 |
| 실제 추출: 15화 < 3분 | 89.4초 (두 화씩 동시) | 실제 실행, `calls.latency_ms` |

| 취소 | 다음 화를 보내지 않고 끝난 화는 남음 | 단위 테스트 |

테스트: 단위 83개, E2E 21개.

## 실제 실행

사용자 키로 M0-A 15화(`D:\LoreWeave-test`, 화당 약 1,200자)를 `gpt-6-luna`로 분석했다. 앱 화면에서 버튼으로 실행했다.

| | 1차 (한 화씩) | 2차 (두 화씩 동시) |
|---|---|---|
| 성공 | 15/15 | 15/15 |
| 저장한 사실 / 버린 사실 | 218 / 1 | 227 / 2 |
| 비용 | $0.0119 | $0.0102 |
| 전체 시간 | 약 3분 0초~3분 8초 (추정) | 89.4초 |
| 호출 시간 | 기록 없음 | 7.6초 / 10.7초 / 15.2초 (최소 / 중앙값 / 최대) |

- **1차에서는 시간 기준을 확인할 수 없었다.** 앱이 호출이 끝난 시각만 남겨서, 첫 화가 끝날 때부터 마지막 화가 끝날 때까지(2분 50초)만 알 수 있었다. 첫 화에 걸린 시간을 다른 화로 추정해 더하면 3분 언저리였다. 그래서 #29에서 호출마다 걸린 시간을 기록하고, 두 화씩 동시에 보내도록 바꿨다. 2차에서 정확히 재 89.4초가 나왔다.
- **2차 비용이 낮은 것은 캐시 때문이다.** 1차는 모든 호출에서 입력이 캐시에 쓰이기만 했고(쓰기 17,200 토큰, 읽기 0), 2차는 같은 본문을 다시 보내 모두 캐시에서 읽혔다(읽기 17,200 토큰). 처음 분석하는 원고의 비용은 1차 값($0.0119, 화당 약 $0.0008)으로 본다.
- 1차 결과는 `D:\LoreWeave-test\.loreweave\ai.db.run1`에 남겨 두었다.

## 만든 것

- **AI 규칙** (`src/core/ai/`): 추출 결과 형식과 검증, 인용 위치 찾기, 비용 계산(캐시 쓰기 포함), 예상 비용 상한. Electron·OpenAI SDK와 무관하다.
  - 추출 프롬프트는 M0-A에서 검증한 문구를 그대로 옮겼다 (해시 `fa2971c6f7e8`, 버전 `extract-1`).
  - 인용 찾기는 NFC, 공백 차이, 곧은/굽은 따옴표, 생략 표시를 허용한다.
- **키와 연결** (`src/main/secrets.ts`, `ai-client.ts`, `settings.ts`): `safeStorage`로 암호화한 키, Responses API + Structured Outputs(strict), 120초 시간 제한, SDK 재시도 3회. 오류는 한국어 안내로 바꾼다.
- **결과 저장소** (`src/main/ai-db.ts`): `.loreweave/ai.db`. 번호 붙은 마이그레이션(현재 형식 2), WAL + `synchronous = FULL`. 깨진 파일은 옮겨 두고, 앱보다 새 형식이면 열지 않는다. AI를 처음 쓸 때만 만든다.
- **분석 실행** (`src/main/analyzer.ts`): 두 화씩 동시에 보낸다. 키·모델·한도 문제는 멈추고, 그 밖의 실패는 그 화만 실패로 남긴다. 호출마다 사용량, 비용, 걸린 시간을 기록한다. 키가 없거나 전송 동의가 없으면 main에서 거부한다.
- **화면**: [설정] 창, [이 화 분석]·[남은 화 분석 (N)] 버튼, 처음 한 번 전송 동의, 여러 화일 때 예상 비용 확인, 진행률과 [취소], 화 목록의 분석 상태 표시(●), 오른쪽 사실 패널과 인용으로 이동.

## M3 중에 정한 것 (DECISIONS)

- 분석은 두 화씩 동시에 보낸다. 한 화씩은 15화에 약 3분이라 기준 경계였다. 한도(429)를 피하려고 2로 둔다.
- 호출마다 걸린 시간을 기록한다 (`calls.latency_ms`, 마이그레이션 2).
- 버튼은 계획의 [바뀐 화 모두 분석] 대신 [남은 화 분석 (N)]으로 했다. 분석하지 않은 화와 분석 뒤 바뀐 화를 함께 보낸다.

## 계획과 달라진 점

- **마이그레이션은 SQL 파일이 아니라 코드 안 배열이다** (`MIGRATIONS`). 빌드에 파일을 따로 싣지 않아도 되고, 항목이 아직 둘뿐이다.
- **실제 호출 확인은 별도 스크립트 대신 앱으로 했다.** 작가가 실제로 쓰는 경로(설정 → 동의 → 확인 창 → 분석)를 그대로 거쳤다.
- **`safeStorage`를 쓸 수 없는 환경에서는 키를 저장하지 않고 AI 기능을 쓸 수 없다고 안내한다.** 계획의 "이번 실행 동안만 쓰기"는 만들지 않았다. Windows에서는 해당하지 않는다.
- 사용량 토큰은 `analyses`가 아니라 `calls`에 둔다. 실패한 호출의 비용도 남기기 위해서다.

## 진행 중 문제와 교훈

- **시간을 잴 수 없는 기록**: 1차 실행 뒤에야 시작 시각이 없다는 것을 알았다. 성공 기준에 시간이 있으면 그 시간을 잴 수 있는 기록을 처음부터 남긴다.
- **동시 실행으로 순서에 기댄 테스트가 흔들림**: "1화가 먼저 끝난다"고 가정한 취소 테스트가 가끔 실패했다. 순서와 무관하게 고치고, 분석 테스트를 20번 반복해 확인했다.
- **PR 운영**: 다음 단계 브랜치는 백업으로만 올려 두고, 앞 PR이 병합된 뒤 main 기준으로 하나씩 열었다. 겹치는 PR 없이 진행됐다.
- OpenAI 사용 비용: M3 실제 실행 2회 합계 약 $0.022.

## 한계와 다음으로 넘기는 것

- **같은 프롬프트를 쓰는데도 화가 바뀌면 캐시를 읽지 못했다.** 1차에서 모든 호출이 캐시 쓰기만 했다. 비용은 기준의 1/5 아래라 M3에서는 두지만, M4에서 호출이 늘면 캐시 설정을 다시 본다.
- **실제 앱에서의 취소는 단위 테스트로만 확인했다.** E2E는 확인 창의 취소까지만 본다.
- **실제 실행의 화는 짧다.** M0-A 화는 약 1,200자로, 연재 웹소설 한 화(보통 5,000자 안팎)의 1/4 정도다. 출력이 본문 길이에 비례한다면 실제 원고에서는 화당 비용과 시간이 몇 배가 된다. 화당 비용은 기준까지 여유가 있지만(약 $0.0008 → 상한 $0.005), 시간은 긴 화로 다시 잰다.
- 실제 실행은 한 컴퓨터, 한 모델(luna)에서만 했다. `gpt-6.1-sol`은 재지 않았다.
- 사실은 볼 수만 있다. 편집·승인, 인물 사전, 다른 화와의 비교는 M4 이후다.
- 다음 단계는 M4(연속성 오류 탐지)다. ADR 0001의 B 전략대로 저장된 사실과 인용을 근거로 쓰고, 오류는 뒤 화로 번지므로(M0-A의 echo) 어느 쪽이 canon인지 작가가 정하게 해야 한다.
