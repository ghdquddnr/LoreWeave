# ADR 0002: 에디터는 TipTap, 원고는 "한 줄 = 한 문단" Markdown, 변환기는 직접 작성한다

- 상태: 채택 (2026-10-24)
- 근거: [M0-B 보고서](../spikes/M0B-REPORT.md)

## 맥락

M0-B에서 TipTap 3.32와 Markdown 변환기 3종을 코퍼스 50개(웹소설 표기 사례 + M0-A 챕터 15개)로 비교했다. 성능과 한글 IME도 Chrome과 Electron에서 확인했다.

| 변환기 | byte 동일 | 문제 |
|---|---|---|
| (a) 공식 `@tiptap/markdown` | 45~57% | `[대사]` 이스케이프, 스키마 밖 문법의 글자를 경고 없이 삭제 |
| (b) 커뮤니티 `tiptap-markdown` | 39~59% | `[대사]` 이스케이프, 줄 합침, 유지보수 중단 |
| (c) 직접 작성 (C3) | 100% | 의미 해석 위험 (아래) |

에디터 자체는 모든 기준을 충족했다. 10만 자까지 입력 지연 p95가 20ms 이하였고, IME 손상은 0건이었다.

## 결정

1. **에디터는 TipTap**(`@tiptap/react`, StarterKit 기반)으로 한다.
   - 입력 규칙과 붙여넣기 규칙을 끈다.
   - 스키마는 문단, 제목, 굵게, 기울임, 구분선, 인용으로 시작한다. 목록, 코드, 링크, 취소선, 밑줄, trailingNode는 끈다.
2. **원고 형식은 C3**다.
   - 한 줄이 한 문단이고, 빈 줄은 빈 문단이다.
   - 알아보는 문법은 줄 시작의 `# `~`###### ` 제목, 정확히 `---`인 구분선, `> `·`>`로 시작하는 연속 줄(인용), 줄 안의 `***`·`**`·`*` 강조뿐이다.
   - 그 밖의 글자는 그대로 둔다. 이스케이프하지 않는다.
3. **Markdown 변환기는 직접 작성한다.** spike 코드는 쓰지 않는다. M1에서 M0-B 코퍼스와 round-trip 검사(byte 동일, 멱등, 국소성)를 먼저 옮긴 뒤 테스트부터 작성한다.
4. **원고 바이트는 에디터 밖에서 지킨다.**
   - BOM, 줄바꿈(CRLF/LF), frontmatter, 마지막 개행은 에디터 밖에서 떼었다 붙인다.
   - 수정하지 않은 파일은 원본 바이트 그대로 저장한다(dirty flag).
5. **저장 전 검사**: 직렬화 결과를 다시 파싱해 글자가 사라지지 않았는지 확인한다. 실패하면 저장하지 않고 알린다.
6. **붙여넣기는 서식을 지우고 글자만** 넣는다. 줄마다 문단이 된다.

## 결과와 남은 질문

- C3 파일은 모든 도구에서 열리고 원문이 그대로 보인다(VISION §4). 다만 **VS Code 미리보기 같은 표준 CommonMark 렌더러는 빈 줄 없는 줄들을 한 문단으로 합쳐 보여 준다.** Obsidian은 기본 설정에서 정상이다. 이 차이는 받아들인다.
- 의미 해석 위험이 있다. 문장이 `# `로 시작하면 제목이 되고, 문장 안 `*` 두 개 사이는 기울임이 된다. 바이트는 보존되지만 화면이 달라진다. M1에서 정할 것:
  - 에디터에서 입력한 `*`를 어떻게 저장할지
  - 줄 시작 `#`을 제목으로 볼 조건
- C3에서 Shift+Enter(강제 줄바꿈)는 저장하면 Enter와 같아진다. 끌지 M1에서 정한다.
- 혼합 줄바꿈 파일은 LF로 통일해 저장한다. 사용자에게 알릴지 M1에서 정한다.
- 저사양 노트북 성능과 MS 한국어 IME 외 입력기는 확인하지 않았다.
- 입력 지연은 문서 길이에 비례한다. 50만 자에서는 약 90ms다. VISION §4 구조(`chapters/001.md`, 한 화 = 한 파일, 보통 5천~1만 5천 자)에서는 여유가 크다.
