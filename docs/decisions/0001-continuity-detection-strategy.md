# ADR 0001: 연속성 오류 탐지는 "Fact + 원문 인용" 방식에서 시작한다

- 상태: 채택 (2026-10-24)
- 근거: [M0-A 보고서](../spikes/M0A-REPORT.md)

## 맥락

M0-A에서 15화짜리 합성 벤치마크(정답 오류 30개, 함정 10개)로 6개 전략을 `gpt-6.1-sol`, `gpt-6-luna`에서 각각 3회씩 비교했다. 사전에 정한 성공 기준 7개를 충족한 조합은 다음과 같다.

| 전략 | sol Recall / Precision | luna Recall / Precision |
|---|---|---|
| full-context (이전 화 전체) | 95% / 92% | 85% / 92% (편차 기준 미달) |
| B. Fact + 원문 인용 | 95% / 100% | 85% / 94% |
| C. 요약 + Fact + 원문 | 95% / 97% | 78% / 92% |

원문 검색 전략(A: FTS5 trigram, D: entity 발췌)은 근거를 입력으로 가져온 비율이 약 40%에 그쳐 Recall 기준에 미달했다. 근거가 입력에 있을 때 모델이 오류를 찾은 비율은 모든 전략에서 73~97%였다.

## 결정

1. M3/M4의 기본 탐지 파이프라인은 **B**로 한다.
   - 화를 저장할 때 한 번 `{entity, predicate, value, quote}`를 추출한다.
   - 검사할 때는 대상 화에 나오는 entity의 이전 Fact를 **원문 인용과 함께** 모델에 준다.
2. **인용문 존재 검사**를 제품의 필수 단계로 둔다. 모델이 낸 `target_quote`와 `evidence.quote`가 원문에 없으면 결과를 표시하지 않는다. 결정론적 검사라 비용이 들지 않고, "근거로 이동" 기능의 전제다.
3. 결과는 항상 "Possible Issue"로 표시하고, 어느 쪽이 canon인지는 사용자가 정한다. 실험에서 오류 하나가 이후의 정상 화까지 경고를 받게 만드는 현상(echo)이 모든 실행에서 나왔기 때문이다.
4. 모델 이름은 설정값으로 둔다. 같은 파이프라인이 작은 모델(luna)에서도 기준을 충족했다.

## 결과와 남은 질문

- full-context는 짧은 원고에서 B와 같은 성능을 내고 더 단순하다. 원고가 짧을 때의 대안으로 남겨 둔다. 다만 비용은 원고 길이에 비례해 늘어난다.
- **장편 규모(60~300화)는 측정하지 않았다.** B가 길이에 덜 민감하다는 것은 추정이다. M3 설계 때 scale probe로 확인한다.
- **한국어 원문 검색은 trigram만으로 부족하다.** 2글자 이름이 검색되지 않는다. M2 검색 설계에서 entity 사전 매칭이나 bigram 같은 보완책을 검토한다. 이 ADR은 검색 방식을 정하지 않는다.
- 합성 벤치마크는 쉬운 편이다. 실제 원고로 소량 sanity check를 해야 한다.
