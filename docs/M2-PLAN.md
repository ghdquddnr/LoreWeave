# M2 계획: SQLite 색인과 원고 검색

M2는 **원고 전체를 검색하고, 결과를 누르면 그 줄로 이동**하는 기능이다. 이를 위해 원고에서 다시 만들 수 있는 정보만 담는 SQLite 색인을 둔다. 원고의 원본은 계속 Markdown 파일이다.

- 근거: VISION §7(SQLite의 역할)·§15(검색), ADR 0001(한국어 trigram 한계), ADR 0002(C3 원고), [M1 결과](M1-REPORT.md)
- 확정한 선택 (2026-10-24, 사용자)
  - 범위: 원고 전체 검색과 결과로 이동. 바꾸기는 제외
  - SQLite: Electron 내장 `node:sqlite` (better-sqlite3에서 변경)
  - 중복 id: 경고와 "새 id 발급" 버튼. 자동으로 파일을 고치지 않는다
  - id 없는 기존 화: 건드리지 않는다. 색인은 파일 이름으로 화를 구분한다

## 1. 범위

**포함**

- 원고 색인: 화마다 줄(= C3 문단) 단위 글자를 SQLite에 담는다. 폴더를 열 때 바뀐 화만 다시 색인하고, 저장할 때와 바깥 변경 때도 갱신한다.
- 검색: 사이드바 검색창 (Ctrl+Shift+F). 결과는 "화 제목 · N번째 줄 · 앞뒤 문맥"이고, 화 순서대로 보여 준다.
- 결과로 이동: 그 화를 열어 해당 줄로 스크롤하고, 찾은 글자를 선택한다.
- 줄 번호 규칙 (M0-B H-B6): 색인과 에디터가 같은 규칙으로 줄을 센다. M4의 "근거로 이동"도 이 규칙을 쓴다.
- 중복 id: 목록 경고 옆에 "새 id 발급" 버튼을 둔다. 고른 화의 frontmatter `id`만 바꾼다.

**제외**: 바꾸기, 정규식·유사어·의미 검색, 인물 사전, AI Fact 저장(M3), 화 밖 문서(설정집 등) 검색, 검색 필터.

## 2. 줄 주소 (core)

- 화 안의 위치는 **본문 줄 번호**(frontmatter를 뺀 본문의 0부터 시작하는 줄)로 가리킨다. C3에서는 한 줄이 한 블록이다. 인용은 예외로, 한 블록이 여러 줄이다.
- `src/core/manuscript`에 두 함수를 둔다.
  - 줄 → 블록 위치: 에디터가 쓴다.
  - 블록 → 줄 범위: 색인과 테스트가 쓴다.
- 색인도 같은 파서(`parseC3`)로 줄 글자를 만든다. 그래서 색인에 담기는 글자는 에디터가 보여 주는 글자와 같다. 강조 구분자 `**`는 빠진 상태다.
- 테스트: M0-B 코퍼스 전체에서 모든 줄에 대해 "색인이 담은 글자 == 에디터 해당 블록의 글자"가 성립해야 한다.

## 3. 색인 (main)

- **위치**: 프로젝트 폴더의 `.loreweave/index.db` (VISION §4의 `.loreweave/` 구조)
  - 화 파일은 건드리지 않는다. 이 폴더만 새로 생긴다.
  - `.loreweave/.gitignore`를 만들어 색인 파일을 버전 관리에서 뺀다.
- **표**
  - `chapters(file, title, id, mtime_ms, size, hash)`
  - `lines(file, line, text)`
- **동기화**
  - 폴더를 열 때 `(mtime, size)`가 다른 화만 다시 읽고, 사라진 화는 지운다.
  - 이 앱이 저장하면, 저장한 글자로 그 화를 다시 색인한다.
  - 바깥에서 바뀌면, M1의 폴더 감시 알림을 받아 다시 색인한다.
  - UTF-8이 아닌 화는 색인하지 않는다.
- **버전과 복구**: `PRAGMA user_version`으로 색인 형식 버전을 둔다.
  - 버전이 다르거나 파일이 깨졌으면 지우고 다시 만든다. 다시 만들 수 있는 정보만 담으므로 마이그레이션이 필요 없다.
  - AI 결과처럼 다시 만들 수 없는 정보는 M3에서 별도 파일과 마이그레이션 방식을 정한다.
- **SQLite 접근**: 한 모듈(`src/main/index-db.ts`)에만 둔다. `node:sqlite` API가 바뀌면 그곳만 고친다.

## 4. 검색 규칙

- **기본은 부분 문자열 일치**다. 2글자 이름(`민수`)도 찾아야 한다. M0-A에서 FTS5 trigram은 3글자 미만을 찾지 못했다.
- **첫 구현은 색인된 줄을 그대로 훑는다** (`instr`). 1000화(약 1천만 자)에서 기준(아래 5절)을 넘으면 그때 FTS5 trigram(3글자 이상)과 짧은 검색어용 훑기를 함께 쓴다. 측정해서 정한다(YAGNI).
- **정규화**: 원고와 검색어를 모두 NFC로 맞춘다. macOS에서 온 파일은 한글이 NFD로 저장돼 있을 수 있다. 영문은 대소문자를 무시한다. 공백은 그대로 비교한다.
- **결과 제한**: 처음 500개까지만 보여 주고 전체 개수를 함께 표시한다.
- **최신성**: 검색하기 직전에 현재 화의 저장 안 된 변경을 먼저 저장한다(flush). 그래서 결과는 화면과 같다.

## 5. 성공 기준

| 항목 | 기준 |
|---|---|
| 검색 정확도 | M0-A 15화에서 `민수`, `지현`, `25.5%`, `"` 등 검색어 20개의 결과가 파일을 직접 훑은 결과와 100% 같다 |
| 줄 주소 | 코퍼스 전체에서 색인 글자 == 에디터 블록 글자 100%. 결과로 이동했을 때 선택된 글자 == 검색어 100% (E2E) |
| 색인 일관성 | 저장, 바깥 변경, 화 추가·삭제 뒤 검색 결과가 파일과 같다 (E2E). 색인 파일을 지워도 다시 만들어진다 |
| 화 파일 보존 | 색인이 화 파일을 바꾸지 않는다 (열기만 하고 닫기 바이트 변화 0 유지) |
| 성능 | 300화 첫 색인 < 2초, 다시 열 때(변경 없음) < 300ms, 저장 후 재색인 < 50ms, 1000화 검색 p95 < 200ms |
| 회귀 | M1 E2E·성능 기준 유지 |

## 6. 진행 순서 (PR은 main 기준으로 하나씩)

1. **core**: 줄 주소 함수, 검색 정규화, frontmatter 필드 바꾸기 (id 재발급용). 테스트 포함
2. **main/색인**: `node:sqlite` 색인, 동기화, 검색 IPC. 임시 폴더 테스트와 1000화 성능 측정
3. **renderer**: 검색창·결과·이동, 중복 id 버튼, E2E
4. **마무리**: 성능 재측정, 결과 문서

## 7. 추가할 라이브러리

없음. `node:sqlite`는 Electron 44(Node 24.22)에 내장돼 있다. FTS5와 trigram 동작도 확인했다(2026-10-24).

## 8. 위험

- **`node:sqlite`가 Node에서 아직 실험 단계일 수 있다**: Electron 버전을 고정하고 접근을 한 모듈에 모은다. 막히면 better-sqlite3로 돌아갈 수 있다(색인은 다시 만들 수 있다).
- **동기화 폴더(OneDrive 등) 안의 색인 파일**: 동기화 충돌로 깨질 수 있다. 깨지면 다시 만든다.
- **`node:sqlite`는 동기 API라 큰 프로젝트의 첫 색인 동안 main이 멈출 수 있다**: 300화 기준으로 재고, 넘치면 나눠서 처리한다.
- **줄 번호가 화면과 어긋나면 "근거로 이동"이 틀린 곳을 가리킨다**: 코퍼스 전체 테스트로 막는다.
