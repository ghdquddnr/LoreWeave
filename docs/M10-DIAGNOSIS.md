## 2. F24와 F25: 내용과 위치 매칭

- **관측** (회차별 저장 응답 대조)
  - real-1: S15 문장에 대해 나이 종류 결과(0.99, 모순을 짚음 = F25)와 숫자 종류 결과(**0.1**, "단정할 수 없다")가 있다.
    - 숫자 종류는 0.7 미만이라 real-1 화면에서는 숨는다.
    - 평가기는 이것을 duplicate로 셌다.
  - real-2: 같은 문장·같은 숫자 종류 결과가 **0.99**이고, claim이 모순을 제대로 짚는다.
- **합치기에서 생긴 일**: 합치기 규칙은 설명을 먼저 나온 결과(real-1)에서, 확신도는 최댓값(real-2)을 쓴다.
  - 그래서 "단정할 수 없다" claim이 0.99로 화면에 보이는 F24가 됐다.
  - 이것은 규칙대로 결정적으로 생기는 일이다. 모델 내부 원인과 무관하다.
- **두 회에 같은 종류·같은 문장으로 나온 결과 쌍** (실제 원고 1쌍 + M4 2쌍): 42개
  - 0.7 문턱을 넘나드는 쌍은 이것 1개다.
  - 확신도가 높은 쪽의 claim으로 바꾸면 claim이 바뀌는 항목은 14개다 (실제 원고 2, M4 12). F24 외 13개는 두 claim 모두 부정 표현이 없다 (정규식 어림, 사람 판정 전).
- **평가기 쪽**: 평가기는 claim을 읽지 않고 위치만 맞춘다. 그래서 위치가 맞으면 부정 claim도 tp·duplicate로 센다.
  - 부정 표현을 정규식으로 찾으면 M8 0, real-1 2, real-2 0, 합친 결과 2, M4 4회 0이다.
  - 사람 판정이 claim을 따로 봐야 하는 이유다 (PR #79 정정과 같다).

## 4. 선정 가설과 고정 검증 계획

**가설**: `mergeFindings`가 같은 종류·같은 문장의 결과를 합칠 때, 설명(claim)을 "먼저 나온 결과"가 아니라 "확신도가 가장 높은 결과"(같으면 먼저 나온 것)에서 가져온다.
- 그러면 화면에 "숨겨질 확신도의 부정 claim + 다른 결과의 높은 확신도" 항목이 생기지 않는다.
- 근거 합치기와 최고 확신도 규칙은 그대로다.

**왜 제품과 관계있나**
- 제품도 한 검사 안에서 나눈 묶음(400개씩)의 결과를 같은 함수로 합친다.
- 다만 묶음별 원래 결과를 저장하지 않아, 제품에서 이런 항목이 얼마나 생기는지는 **불명**이다.
- 관측은 두 회 합치기에서 1건이다.

**반례와 위험**
- 확신도가 높은 쪽의 claim이 늘 더 맞다는 보장은 없다. 이번 14개 중 F24 외 13개는 두 claim 모두 부정 표현이 없지만(정규식 어림), 어느 쪽이 더 정확한지는 판정하지 않았다.
- 바뀌는 claim이 작가에게 다르게 읽힐 수 있다. claim 차이는 사람이 확인해야 한다.
- TP·오탐 수에는 영향이 없을 것으로 본다 (평가기는 claim을 읽지 않음). 그래서 사람 판정이 바뀌는지가 기준이다.
- 이 가설은 **Recall을 올리지 않는다.** R2 미달(S09·S18·S20)과는 무관하다.

**고정 비교 대상과 기준** (구현 PR에서, 호출 0)
- **비교 대상**: 저장된 결과를 지금 규칙과 바꾼 규칙으로 각각 합친다.
  - M10 실제 원고 real-1+real-2
  - M10 M4 두 쌍 (1+2, 3+4)
  - M9의 같은 조건 두 회 9쌍 (비공개 복사본)
- **기준** (실행 전 고정):
  1. 평가기 TP·오탐·중복 수가 쌍마다 지금 규칙과 같다.
  2. 0.7 미만인 원래 결과의 claim이 0.7 이상 항목의 claim으로 쓰이는 경우가 0이다 (지금 규칙: 실제 원고 1건).
  3. claim이 바뀐 항목은 모두 사람이 판정한다. 바뀐 claim이 모순을 부정하는 경우가 0이다.
  4. 제품 단위 테스트를 추가한다: 한 검사 안 묶음 합치기에서 "낮은 확신도 부정 claim + 높은 확신도"를 합치면 높은 쪽 claim이 남는다. 기존 E2E·단위 테스트는 모두 통과해야 한다.
- **실패 시**: 기준 1이나 3이 어긋나면 바꾸지 않고 멈춘다.
- **반복 기준선**: 이 가설은 호출하지 않으므로 필요 없다. 이후의 판단 쪽 유료 검증은 이번 M10 두 회를 기준선으로 쓴다.
- **최대 호출 0 / 보수 상한 $0 / 단계 중단 상한 해당 없음.** 유료 실행이 필요 없다.
- **제품 변경이 들어간다** (`src/core/ai/verify.ts`). 그래서 구현은 감독이 따로 정한다. 이 PR은 계획뿐이다.

## 5. Recall 쪽: 불명과 필요한 최소 검증

- **지금 자료로는 S09·S18·S20 같은 회 간 누락을 줄일 방법을 정할 수 없다.**
  - 같은 입력에서 M8은 찾고 이번 두 회는 못 찾았다. 그 이유는 출력에 남지 않는다.
- **필요한 최소 검증 1** (호출 0, 구현만): runner가 다음을 저장소 밖 작업 폴더에 저장하게 한다.
  - 묶음별 원래 결과
  - 위치 검증으로 버린 결과의 내용
  - 그래야 다음 실행에서 S05·S20처럼 "버린 결과가 그 오류였는지"를 판별할 수 있다.
- **필요한 최소 검증 2** (유료, 지금 제안하지 않음): 판단 쪽 후보(예: detect-2)를 검증하려면 같은 입력에서 대조군과 후보를 각각 2회 이상 돌려야 한다.
  - 실제 원고 한 회는 128호출, 보수 상한 $2.689이다.
  - 대조군 2 + 후보 2 = 512호출, 보수 상한 $10.75(재시도 0)다. 단계 중단 상한 $1.20보다 훨씬 크다.
  - M10 실측(첫 회 $0.469, 같은 입력 반복 $0.055)으로 어림하면 약 $1.05다. 한도 안 완주는 보장되지 않는다.
  - 후보는 프롬프트가 달라 캐시가 적용되지 않을 수 있다.
  - 실행 여부는 근거가 생긴 뒤 별도 승인 대상이다.

- 부정 claim 찾기는 정규식 어림이다.
