# M4 계획: 연속성 오류 탐지

M4는 **작가가 [이 화 검사]를 누르면, 그 화가 이전 화에서 정한 설정과 부딪히는 곳을 근거 문장과 함께 "문제 가능성"으로 보여 주는** 단계다. INTENT §17의 첫 번째 성공 기준("새 Chapter에서 이전 Chapter와 충돌하는 설정을 실제로 찾아낼 수 있는가")을 제품에서 확인한다. M4까지가 v0.1이다.

- 근거: [ADR 0001](decisions/0001-continuity-detection-strategy.md) (B 전략, 인용문 존재 검사, 결과는 Possible Issue), [M0-A 보고서](spikes/M0A-REPORT.md), [M3 결과](M3-REPORT.md), INTENT §3·§4·§5·§13·§18
- 확정한 선택 (2026-10-25, 사용자)
  - 실행: [이 화 검사] 버튼. 현재 화를 그 앞의 화들과 비교한다. 분석이 안 됐거나 분석 뒤 바뀐 화는 먼저 분석하고, 그 비용까지 합쳐 확인받는다
  - 결과 처리: 보기와 [무시]. 무시한 결과는 다시 검사해도 숨긴다. 어느 쪽이 맞는지는 작가가 원고를 고쳐서 정한다
  - 모델: 추출과 같은 설정 모델 하나를 쓴다 (기본 `gpt-6-luna`)
  - 표시: 오른쪽 패널의 목록. 본문 밑줄은 하지 않는다

## 1. 범위

**포함**

- **[이 화 검사]**: 현재 화와 그 앞의 화들이 모두 분석돼 있어야 한다.
  - 분석이 필요한 화가 있으면 "화 N개 분석 + 검사, 예상 비용 최대 $X"로 확인받은 뒤, 분석(M3, 두 화씩 동시)과 검사를 이어서 한다.
  - 모두 분석돼 있으면 검사 비용만 보여 주고 확인받는다.
  - 1화는 비교할 앞 화가 없어 검사하지 않는다.
- **탐지** (B 전략): 검사할 화에 나오는 인물·대상(별칭 포함)의 이전 화 사실을 원문 인용과 함께 모델에 주고, 모순을 찾게 한다.
  - 탐지 프롬프트는 M0-A에서 검증한 문구를 그대로 옮긴다 (해시 `53207cd406ae`, 출처 태그 `spike-m0a-2026-10-24`). 결과에 프롬프트 버전을 남긴다.
  - 인물 이름 맞추기도 M0-A와 같다: 2글자 이상이고 한쪽이 다른 쪽을 포함하면 같은 인물로 본다 ("민수" ~ "김민수").
- **결과 검증** (ADR 0001 결정 2): 모델이 낸 문장이 실제 원고에 있는지 확인한다.
  - 검사한 화의 문장(`target_quote`)이 그 화에 없으면 결과를 버린다.
  - 근거 문장(`evidence`)은 그 화에 있는 것만 남긴다. 남는 근거가 없으면 결과를 버린다.
  - 버린 개수를 기록하고 패널에 보여 준다.
- **문제 가능성 패널** (오른쪽, 사실 패널 위): 결과마다
  - 종류(나이, 첫 만남, 숫자 등), 설명(`claim`), 확신도(작게, 보조 정보)
  - 이 화의 문장 → [이동], 근거마다 "N화: 문장" → [N화로 이동]. M2·M3의 이동을 그대로 쓴다
  - [무시]. 무시한 결과 수와 [무시한 결과 보기]
  - 표시는 항상 "문제 가능성"이다. "오류"라고 단정하지 않는다
- **검사 상태**: 검사 안 함 / 검사 뒤 그대로 / 검사 뒤 바뀜. 검사한 화나 근거로 쓴 앞 화의 본문이 바뀌면 "바뀜"이고, 패널에 다시 검사하라고 알린다.
- **측정 도구**: 검사 결과를 M0-A 채점기의 입력 형식(`predictions.json`)으로 내보내는 스크립트. 채점은 main에 남아 있는 M0-A 채점기(`spikes/m0a-ai-feasibility/src/evaluate.ts`)로 한다.

**제외 (v0.1 이후)**: [전체 검사], 본문 밑줄, "앞 화 쪽이 틀렸다" 표시(echo 차단), 이후 화와 비교, 사실 편집·인물 사전, 자동 검사, 다른 AI 제공자, 설치 파일.

## 2. 구조

| 위치 | 내용 |
|---|---|
| `src/core/ai/detection.ts` | 탐지 프롬프트(M0-A 원문), 출력 형식과 검증, 앞 화 사실 고르기(인물 맞추기), 입력 만들기 |
| `src/core/ai/verify.ts` | 결과 검증: 문장 위치 찾기(M3 `locateQuote`), 근거 거르기 |
| `src/core/ai/cost.ts` | 검사 예상 비용 상한 (입력: 이 화 + 고른 사실, 출력 상한) |
| `src/main/checker.ts` | 검사 실행: 필요한 분석 → 사실 고르기 → 호출 → 검증 → 저장 |
| `src/main/ai-db.ts` | 마이그레이션 3: 검사 결과, 무시 목록 |
| `src/renderer/` | [이 화 검사], 확인 창, 문제 가능성 패널, 다른 화로 이동 |
| `scripts/export-predictions.ts` | `ai.db`의 검사 결과 → `predictions.json` |

- **화 번호**: 탐지 입력과 근거의 화 번호는 파일 이름의 번호(M1 `chapterNumber`)다. 근거의 화 번호로 파일을 찾는다.
- **앞 화**: 파일 이름 번호가 더 작은 화. 화 순서는 M1 규칙(파일 이름 번호)을 따른다.

## 3. 저장 (`ai.db` 마이그레이션 3)

- `checks(id, file, content_hash, model, model_version, prompt_version, fact_count, dropped, cost_usd, created_at)`: 화마다 마지막 검사. 다시 검사하면 바꾼다
- `check_inputs(check_id, file, content_hash)`: 근거로 넘긴 앞 화와 그때의 본문 해시 ("검사 뒤 바뀜" 판단용)
- `findings(check_id, ord, category, claim, confidence, target_quote, line, start_col, end_col)`
- `finding_evidence(check_id, finding_ord, ord, file, quote, line, start_col, end_col)`
- `dismissals(file, category, target_key, created_at)`: 무시한 결과. `target_key`는 정규화한 `target_quote`다.
  - 다시 검사해서 같은 화, 같은 종류, 같은 문장이 나오면 숨긴다.
  - 작가가 그 문장을 고치면 키가 달라져 다시 보인다. 한 문장에 종류가 같은 다른 문제가 있으면 함께 숨는 한계가 있다.
- 검사 호출도 M3의 `calls`에 사용량, 비용, 걸린 시간을 남긴다.

## 4. 비용과 실패

- **예상 비용 상한**: 분석이 필요한 화의 추출 상한(M3) + 검사 상한. 검사 입력은 이 화 본문 + 고른 사실을 글자 수로 센다.
- **실패**: M3와 같다. 키·모델·한도 문제는 멈추고 안내한다. 앞 화 분석이 하나라도 실패하면 검사하지 않는다 (빠진 사실로 검사하면 놓친 오류를 "문제 없음"으로 보이게 한다).
- **결과가 없을 때**: "찾은 문제 가능성이 없습니다"와 함께 비교한 앞 화 수, 사실 수를 보여 준다. 검사하지 않은 것과 구분한다.

## 5. 성공 기준

| 항목 | 기준 |
|---|---|
| 탐지 품질 (M0-A 벤치마크 test, luna, 앱으로 2~15화 검사) | Recall ≥ 75%, Precision ≥ 85%, 화당 FP ≤ 0.3, test 함정 오탐 ≤ 1개 |
| 근거 | 보여 준 결과의 문장과 근거가 모두 원고에 있다. TP의 근거 화 정확도 ≥ 90% |
| 비용·시간 (luna) | 검사 한 번 ≤ $0.005, < 30초 (앞 화가 모두 분석된 상태) |
| 결과 검증 | 원고에 없는 문장이나 근거만 가진 결과는 저장하지 않는다 (단위 테스트, 가짜 응답) |
| 이동 | 이 화 문장과 근거 문장을 누르면 그 화가 열리고 선택된 글자가 인용과 같다 (E2E) |
| 무시 | 무시한 결과는 다시 검사해도 숨는다. 문장을 고치면 다시 보인다 (단위 테스트, E2E) |
| 검사 상태 | 검사한 화나 근거로 쓴 앞 화가 바뀌면 "바뀜"으로 보인다 (단위 테스트, E2E) |
| 원고 보존, AI 없이 동작 | M3와 같다. 검사가 화 파일을 바꾸지 않고, 키 없이 M1~M3 E2E가 그대로 통과한다 |

- **탐지 품질 기준의 근거**: M0-A의 B + luna는 Recall 85%, Precision 94%, 화당 FP 0.07, 함정 오탐 0이었다. 3회 반복 편차가 10%p였고 test 오류가 20개뿐이라, 제품 구현이 M0-A와 같다고 볼 수 있는 하한으로 정했다.
  - 제품은 M0-A와 다르게 근거가 원고에 없는 결과를 버린다. Precision은 오르고 Recall은 조금 내려갈 수 있다.
- **측정 방법**
  - 시험 원고(`D:\LoreWeave-test`)를 M0-A 원본 15화로 되돌린다. 3·9·11화에 M1 IME 테스트 글자가 남아 있다.
  - 작가가 앱에서 2~15화를 차례로 [이 화 검사]한다.
  - 결과를 `predictions.json`으로 내보내 M0-A 채점기로 채점한다. 비용은 약 $0.01~0.03로 본다.
  - 측정은 1회다. 반복 편차는 재지 않는다 (한계로 보고서에 적는다).

## 6. 진행 순서 (PR은 main 기준으로 하나씩)

1. **core/ai**: 탐지 프롬프트와 출력 형식, 앞 화 사실 고르기, 결과 검증, 검사 예상 비용
2. **main/검사**: 마이그레이션 3, 검사 실행(필요한 분석 포함), 검사 상태, 무시, IPC. 가짜 클라이언트로 테스트
3. **renderer**: [이 화 검사]와 확인 창, 문제 가능성 패널, 다른 화로 이동, 무시
4. **측정과 결과 문서**: 내보내기 스크립트, 시험 원고 복원, 작가가 2~15화 검사, 채점, M4 보고서, v0.1 표시

## 8. 위험

- **echo**: 앞 화의 오류 하나 때문에 뒤의 정상 화들이 경고를 받는다 (M0-A에서 매번 나옴). M4에서는 작가가 앞 화를 고치거나 [무시]로 처리한다. 결과가 많아 불편하면 "앞 화 쪽이 틀렸다" 표시를 다음 단계에서 검토한다.
- **긴 연재에서 입력이 커진다**: 주인공처럼 자주 나오는 인물은 앞 화 사실이 화 수에 비례해 늘어난다. M0-A는 15화만 쟀다. 검사마다 넘긴 사실 수와 입력 토큰을 기록해 두고, 실제 원고에서 커지면 상한(최근 화 우선 등)을 다음 단계에서 정한다.
- **놓친 오류가 "문제 없음"처럼 보인다**: 결과가 없을 때 무엇과 비교했는지(앞 화 수, 사실 수)를 함께 보여 준다. 표현이 바뀐 모순이나 계산이 필요한 모순(M0-A의 E05, E25, E26)은 luna가 자주 놓친다.
- **오탐에 지친다** (INTENT §18): 함정 오탐을 기준에 넣었고, [무시]로 같은 결과를 다시 보지 않게 한다.
- **원고가 외부로 전송된다**: M3와 같다. 버튼을 누를 때만 보내고, 처음 한 번 동의를 받는다. 검사는 이 화 본문과 앞 화 사실(원문 인용 포함)을 보낸다.
