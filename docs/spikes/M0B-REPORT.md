## 결론

**성공 기준 충족. TipTap을 유지한다.** 단, 조건이 있다. 원고 형식은 **C3(한 줄 = 한 문단)** 이고, Markdown 변환기는 **직접 작성**한다. TipTap 공식 변환기와 커뮤니티 변환기는 원고를 바꾸거나 글자를 지워서 기준에 미달했다.

| 기준 (M0-PLAN §3) | 결과 | 판정 |
|---|---|---|
| 무수정 open→save byte 동일 100% | dirty flag로 100%. 변환기 자체도 (c) 직접 작성 · C3는 49/49 | 충족 |
| 한 문단 수정 시 나머지 문단 byte 동일 100% | (c) 100% | 충족 |
| 직렬화 멱등성 100% | (c) 100% | 충족 |
| 텍스트 손실·원치 않는 이스케이프 0건 | (c) 0건 (예외: 혼합 줄바꿈 1건, 문서화) | 충족 |
| IME 체크리스트 (30분 입력 포함) 데이터 손상 0건 | 시나리오 12개 Chrome·Electron 통과, 30분 입력 손상 0건 (사용자 수동 검증) | 충족 |
| 입력 지연 p95 < 50ms (5천~2만 자) | Chrome 5.4ms / Electron 5.0ms (최악 위치) | 충족 |
| 입력 지연 p95 < 100ms (10만 자) | Chrome 18ms / Electron 16ms | 충족 |
| 로드 < 1초 (2만 자) | Chrome 36ms / Electron 34ms | 충족 |
| Undo/Redo, 붙여넣기 체크리스트 | 전 항목 통과 (사용자 수동 검증). 파일 연 직후 Ctrl+Z에도 문서 유지 | 충족 |

1~3행은 (a)(b)로는 미달이다. M0-PLAN의 철회 조건("1~3행 미달 시 TipTap 철회")은 변환기를 직접 작성하는 조건으로 피했다. 에디터 자체(ProseMirror 문서 모델, 입력, 성능)에는 문제가 없었고, 문제는 Markdown 변환 계층에만 있었다.

## 가설 검증

| 가설 | 결과 |
|---|---|
| H-B1 무수정 open→save byte 동일 | **지지.** dirty flag로 보장하고, 변환기 (c)는 dirty flag 없이도 49/49 |
| H-B2 한 문단 수정 시 diff는 그 문단에만 | **(c)에서 지지.** (a)(b)는 변환기가 편집을 퍼뜨리지는 않지만, byte 동일이 아닌 파일(약 절반)은 어느 문단을 고쳐도 다른 곳의 변형이 함께 저장된다 |
| H-B3 한글 IME 입력 손상 없음 | **지지.** MS 한국어 IME, Chrome·Electron 각각 12개 시나리오, 30분 입력 손상 0건 |
| H-B4 긴 챕터에서 입력 지연 허용 범위 | **지지.** 10만 자까지 p95 20ms 이하. 50만 자는 약 90ms (기준 밖 참고) |
| H-B5 Undo/Redo·붙여넣기가 집필 UX를 해치지 않음 | **지지.** 단 히스토리가 500ms 안의 변경을 묶는다 (아래 "관찰") |
| H-B6 인덱서와 에디터가 같은 방식으로 문단을 셈 | **측정 안 함.** C3에서는 원고 한 줄이 에디터 블록 하나라 (인용 제외) 둘이 같은 규칙을 쓰기 쉽다. M2에서 확인 |

## 변환기 비교

코퍼스 50개 (직접 작성 35개 + M0-A 챕터 15개), 변환 결과를 실제 TipTap 에디터에 넣었다 꺼내 검사했다.

| 조합 | byte 동일 | 멱등 | 주요 문제 |
|---|---|---|---|
| (a) 공식 `@tiptap/markdown` · C1 / C2 / C3 | 49% / 45% / 57% | 94~96% | `[대사]` → `\[대사\]`. 스키마에 없는 문법의 **글자를 경고 없이 지움** (`1. 첫째…` 줄, 들여쓴 줄, `` `sudo` ``) |
| (b) 커뮤니티 `tiptap-markdown` · C1 / C2 / C3 | 41% / 39% / 59% | 98~100% | `[대사]` 이스케이프, C1에서 줄바꿈 하나를 공백으로 합침, C3에서 빈 줄이 NBSP 글자 문단이 됨. **작성자가 유지보수 중단 공지** |
| (c) 직접 작성 · C3 | **100%** | 100% | 없음 (설계상). 의미 해석 위험은 아래 |

- 두 기성 변환기 모두 M0-A 챕터 15개 중 6개를 바꾼다. 원인은 문자 메시지·시스템창 표기 `[ ]`의 이스케이프다. 웹소설에서 흔한 표기다.
- 두 변환기의 공통 변형: `***`·`* * *` → `---`, 닫히지 않은 `**` → `\*\*`, `<b>` → `**`, 빈 줄 없이 쓴 `---`가 위 줄을 제목으로 만든다.
- (c)는 알아보는 문법(`# ` 제목, 정확히 `---`, `> ` 인용, `*`·`**` 강조)만 노드로 바꾸고 나머지는 글자 그대로 둔다. 이스케이프는 하지 않는다.

## 빈 줄 규약: C3 채택

| | C1 표준 CommonMark | C3 한 줄 = 한 문단 |
|---|---|---|
| 웹소설 원고 관행 (한 줄 = 한 문단, 빈 줄 = 여백) | 연속 빈 줄·한 줄 문단이 사라짐 | 그대로 |
| LoreWeave 안에서 | 변환기 (a)·(b)의 변형을 받아들여야 함 | byte 보존 |
| Obsidian | 정상 | 정상 (사용자 확인, 기본 설정) |
| VS Code 미리보기 | 정상 | **빈 줄 없는 줄들이 한 문단으로 합쳐 보임** (사용자 확인). 원문 편집 화면은 그대로 |
| 일반 텍스트 편집기 | 정상 | 정상 |

VISION §4의 요구는 "LoreWeave 없이도 다른 도구에서 열고 읽을 수 있어야 한다"이다. C3 파일은 모든 도구에서 열리고 원문이 그대로 보인다. 표준 렌더러의 미리보기에서 문단이 합쳐지는 것은 받아들인다. 사용자 결정 (2026-10-24).

## 성능

production 빌드, Chrome 155와 Electron 44 (Chromium 152)를 번갈아 5회씩 잰 중앙값이다. Ryzen 9 3900X에서 측정했다.

| 원고 | 블록 | 입력 지연 p95 (최악 위치) | 로드 | 2만 자 붙여넣기 | 실행 취소 |
|---|---|---|---|---|---|
| 5천 자 | 261 | 3~5ms | 21ms | 18ms | 8ms |
| 2만 자 | 1,041 | 5ms | 35ms | 17ms | 10ms |
| 10만 자 | 5,183 | 16~18ms | 90ms | 26ms | 14ms |
| 50만 자 | 25,949 | 92~98ms | 370ms | 84ms | 66ms |

- 측정 검증: 렌더된 블록 수, 입력 글자 수, 붙여넣기·실행 취소 결과 불일치 0/120회. 페이지 오류 0건.
- 입력 지연은 블록 수에 거의 비례한다. 50만 자 프로파일에서 JS는 키당 약 8ms (주로 ProseMirror 화면 갱신)이고, 나머지는 브라우저 렌더링으로 보인다 (레이아웃을 따로 나눠 재지는 않음).
- 웹소설 한 화는 보통 5천~1만 5천 자다. 한 파일 = 한 화 구조라면 여유가 크다. 한 파일에 수십 화를 넣는 사용 방식은 M1에서 막거나 경고할지 정한다.
- 변환기별 로드 차이는 작다 (2만 자: 25~36ms).

## 관찰 (M1 설계 입력)

1. **붙여넣기는 서식을 지우고 글자만** 넣는다 (사용자 결정). 줄마다 문단으로 들어간다.
2. **히스토리 묶음 500ms**: 입력 직후 0.5초 안에 붙여넣고 실행 취소하면 앞의 입력까지 함께 취소된다. 붙여넣기 전에 히스토리를 끊을지 M1에서 정한다.
3. **TipTap `focus()`는 다음 프레임에 적용된다.** 프로그램으로 커서를 옮긴 직후의 키 입력은 에디터에 들어가지 않는다 (예: "근거로 이동" 직후 바로 타이핑).
4. **(c)의 의미 해석 위험**: `# 해시태그로 시작하는 문장`은 제목이 되고, `5*5=25, 그리고 2*3`은 사이가 기울임이 된다. 바이트는 그대로지만 화면이 달라진다. 작가가 에디터에서 친 `*`가 다시 열 때 강조로 읽힐 수도 있다.
5. **C3에서 Shift+Enter(강제 줄바꿈)는 저장하면 Enter와 같다** (다시 열면 두 문단). 강제 줄바꿈을 끌지 정한다.
6. **혼합 줄바꿈(CRLF+LF) 파일**은 저장 시 LF로 통일된다 (문서화된 예외). 사용자에게 알릴지 정한다.
7. 변환기 (a)의 "경고 없는 글자 삭제"는 변환 결과를 쓰기 전에 **글자 수 검증**이 필요하다는 근거다. 직접 작성하는 변환기에도 저장 전 검사(직렬화 → 재파싱 → 글자 비교)를 둔다.

## 한계

- 성능은 빠른 데스크톱 한 대에서 쟀다. 저사양 노트북은 측정하지 않았다. 측정 중 대기 상태의 Vite 개발 서버 하나가 떠 있었다.
- 한글 IME 조합 입력의 지연은 자동 측정에 포함되지 않았다 (손상 여부만 수동 확인).
- 입력기는 MS 한국어 IME만 시험했다.
- 코퍼스는 직접 만든 사례다. 실제 연재 원고 파일로 round-trip을 확인해야 한다.
- 붙여넣기는 사용자가 출처별로 확인했고, 자동 회귀 테스트는 없다.

## 유지 / 폐기 (M0-PLAN §7)

- **유지**: 코퍼스와 round-trip 검사(회귀 테스트로 재사용), 수동 체크리스트와 결과, `results/`, 이 보고서, ADR 0002
- **폐기 예정**: 검증 패널(Vite 앱), 측정 페이지·러너, Electron 창, 변환기 (a)(b). 변환기 (c)도 M1에서 코퍼스를 기준으로 테스트부터 다시 작성한다. 정리 전에 태그로 보존한다.
