## 결론

**M4 성공 기준을 모두 충족했고, 이로써 v0.1이 완성됐다.** 작가가 [이 화 검사]를 누르면 그 화가 앞 화에서 정한 설정과 부딪히는 곳을 근거 문장과 함께 "문제 가능성"으로 보여 준다. 이 화 문장이나 근거를 누르면 그 화의 그 문장으로 이동한다. INTENT §17의 첫 번째 성공 기준("새 Chapter에서 이전 Chapter와 충돌하는 설정을 실제로 찾아낼 수 있는가")을 합성 벤치마크에서 제품으로 확인했다.

| 기준 (M4-PLAN 5절) | 결과 | 확인 방법 |
|---|---|---|
| Recall ≥ 75% (test) | **90%** (20개 중 18개) | 실제 실행, M0-A 채점기 |
| Precision ≥ 85% | **100%** (오탐 0) | 같음 |
| 화당 FP ≤ 0.3 | **0** | 같음 |

| 원고 보존, AI 없이 동작 | 검사가 화 파일을 바꾸지 않음. 키 없이 M1~M3 E2E 통과 | 단위 테스트, E2E |

## 실제 실행

- 시험 원고: M0-A 벤치마크 15화 (`D:\LoreWeave-test`, 정답 오류 30개·함정 10개). 측정 전에 15화가 모두 원본과 같은지 확인했다.
- 작가가 앱에서 2~15화를 차례로 [이 화 검사]했다. 모델은 `gpt-6-luna`.
- 앞 화 분석은 M3 실행 때 저장된 결과를 그대로 썼고, 원본으로 되돌린 3·9·11화만 검사 전에 다시 분석됐다.
- 결과를 `scripts/export-predictions.ts`로 내보내 main에 남아 있는 M0-A 채점기(`spikes/m0a-ai-feasibility/src/evaluate.ts`)로 채점했다.

| Recall (test) | 90% | 85% | 95% |
| Precision | 100% | 94% | 100% |

- 검사 결과 26개 중 24개가 정답 오류(dev 6, test 18), 2개가 echo였다. 원고에 없는 문장 때문에 버린 결과는 없었다 (14화 모두 0).
- **비용**: 검사 14회 $0.0139, 다시 분석한 3화 $0.0024, 합계 $0.016.
- **시간**: 검사 한 번 최대 8.4초. 14화 전체가 약 4분 걸렸고, 대부분은 작가가 화를 고르고 버튼을 누르는 시간이었다.

## 만든 것

- **탐지 규칙** (`src/core/ai/detection.ts`, `verify.ts`)
  - M0-A 탐지 프롬프트를 그대로 옮겼다 (해시 `53207cd406ae`).
  - 앞 화 사실은 이름 맞추기로 고르고, 입력은 M0-A B 전략과 같은 형식이다. M0-A 실제 입력 30건과 비교해 같았다 (검사할 화 제목의 `# ` 기호만 다름).
  - 결과 검증: 이 화 문장과 근거 문장이 원고에 있어야 남긴다.
- **검사 실행** (`src/main/checker.ts`)
  - 분석이 안 됐거나 바뀐 화를 먼저 분석한다. 앞 화 분석이 하나라도 실패하면 검사하지 않는다.
  - 검사 상태(없음/그대로/바뀜)를 판단하고 무시 목록을 관리한다.
  - `ai.db` 마이그레이션 3을 추가했다.
- **화면**
  - [이 화 검사]와 확인 창: 먼저 분석할 화, 예상 비용 상한
  - 오른쪽 "문제 가능성" 패널: 종류, 설명, 확신도, 이 화·근거로 이동, [무시], 무시한 결과 보기
- **측정 도구** (`scripts/export-predictions.ts`, `pnpm export:predictions`): `ai.db`의 검사 결과를 M0-A 채점기 입력으로 내보낸다. 모델이 본 앞 화 사실(context)도 함께 내보내 retrieval·judge를 나눠 볼 수 있다.

## M4 중에 정한 것 (DECISIONS)

- 무시 키는 원고에서 찾은 이 화 문장으로 만든다. 공백, 따옴표 모양, 문장을 감싼 따옴표가 있는지는 같게 본다.
- 화 번호가 같은 파일(`003.md`와 `3.md`)이 있으면 검사하지 않는다. 근거의 화 번호로 파일을 찾을 수 없기 때문이다.
- 분석과 검사는 한 번에 하나만 실행하고, 키와 전송 동의 검사를 한 곳에서 한다.

## 진행 중 문제와 교훈

- **무시가 다시 검사하면 풀림**: 모델이 같은 대사를 따옴표째 인용하기도 하고 빼고 인용하기도 했다. 단위 테스트가 잡았고, 키에서 감싼 따옴표를 뺐다.
- **따옴표 두 겹 표시**: 대사 인용이 `“"…"”`로 보였다. 스크린샷으로 확인해 고쳤다.
- **측정 스크립트가 사라진 것처럼 보임**: 작가가 앱을 실행하려고 같은 폴더를 `main`으로 바꿔, 측정 브랜치의 스크립트가 작업 폴더에 없었다. 브랜치를 되돌려 해결했다. 작가가 앱을 실행하는 폴더와 다음 작업 브랜치가 같은 폴더라는 점을 다음 측정 때 미리 알린다.

## 한계와 다음으로 넘기는 것

- **측정은 1회다.** M0-A의 luna 반복 편차가 10%p였으므로 90%와 85%의 차이는 의미가 없다. "M0-A와 같은 수준을 제품에서 재현했다"까지가 결론이다.
- **합성 벤치마크다.** 문체가 균질하고 오류가 깔끔하게 들어가 있다. 실제 원고로 소량 확인이 필요하다 (ADR 0001의 남은 질문).
- **긴 연재에서 입력이 커진다.** 앞 화 사실 수가 화마다 약 11개씩 늘어 15화에서 163개, 입력 10,223토큰이었다. 이대로면 300화에서 사실 3천 개 이상, 입력 20만 토큰 안팎이 돼 비용과 정확도 모두 문제가 된다. 사실 수 상한(최근 화 우선, 같은 속성의 최신 값만 등)을 다음 단계에서 정하고 측정한다.
- **echo는 작가가 앞 화를 고치거나 무시해야 사라진다.** "앞 화 쪽이 틀렸다" 표시는 결과가 많아 불편할 때 검토한다.
- 놓치는 유형(표현이 바뀐 모순, 계산이 필요한 모순, 장소)은 luna의 한계로 보인다. 설정에서 sol을 고르면 나아질 수 있으나(M0-A 95%), 비용이 약 20배다.
- 설치 파일은 v0.1 범위가 아니다. 지금은 `corepack pnpm dev`로 실행한다.
