# M2 결과: SQLite 색인과 원고 검색

- 날짜: 2026-10-25
- 계획: [`M2-PLAN.md`](M2-PLAN.md)
- PR: #20 (줄 주소·검색 규칙), #21 (색인·검색), #22 (검색 화면·이동·중복 id)

## 결론

**M2 성공 기준을 모두 충족했다.** 원고 전체를 검색하고 결과를 누르면 그 화의 그 줄로 이동해 찾은 글자가 선택된다. 2글자 이름도 찾는다. 색인은 원고에서 다시 만들 수 있는 정보만 담고, 화 파일을 바꾸지 않는다.

| 기준 (M2-PLAN 5절) | 결과 | 확인 방법 |
|---|---|---|
| 검색 정확도: 검색어 20개 결과 == 파일을 직접 훑은 결과 | 20개 모두 같음 (`민수`, `지현` 등 2글자 이름 포함) | 단위 테스트 |
| 줄 주소: 색인 글자 == 에디터 블록 글자 | 코퍼스 65개(M0-B 50 + M0-A 15) 모든 줄에서 같음 | 단위 테스트 |
| 결과로 이동: 선택된 글자 == 검색어 | "지현" 결과 30개 모두 정확히 선택 | E2E |
| 색인 일관성: 저장·바깥 변경·추가·삭제 뒤 결과 == 파일 | 저장 전 입력, 바깥에서 고친 글자 모두 검색됨 | 단위 테스트, E2E |
| 색인 복구 | 깨진 파일, 비운 파일, 형식 버전이 다른 파일을 다시 만듦 | 단위 테스트, E2E |
| 화 파일 보존 | 색인이 화 파일을 바꾸지 않음. `.loreweave/`만 생김 | 단위 테스트, M1 E2E |
| 300화 첫 색인 < 2초 | 663ms | `pnpm perf:index` |
| 다시 열 때 (변경 없음) < 300ms | 21ms (300화), 68ms (1000화) | `pnpm perf:index` |
| 저장 후 재색인 < 50ms | 4.4ms | `pnpm perf:index` |
| 1000화 검색 p95 < 200ms | 146ms (500만 자) | `pnpm perf:index` |
| M1 회귀 | 2만 자 열기 98ms, 입력 지연 p95 6.7ms, 300화 목록 339ms (모두 기준 안) | `pnpm perf`, E2E 16개 |

테스트: 단위 58개, E2E 16개. 성능은 Ryzen 9 3900X 한 대에서, 화당 5천 자 원고로 쟀다.

## 만든 것

- **줄 주소** (`src/core/manuscript/lines.ts`)
  - 화 안의 위치는 본문 줄 번호로 가리킨다.
  - 색인과 에디터가 같은 함수로 줄을 센다. M0-B에서 미뤄 둔 H-B6(색인과 에디터가 같은 방식으로 문단을 세는가)을 설계와 테스트로 해결했다.
  - M4의 "근거로 이동"이 이 규칙을 그대로 쓴다.
- **검색 규칙** (`src/core/search.ts`)
  - 부분 문자열 일치에 NFC 정규화와 영문 대소문자 무시를 적용한다.
  - 찾은 위치는 원래 글자 기준으로 돌려준다. 글자 덩어리(grapheme) 단위로 대응시키기 때문에, NFD로 저장된 원고와 이모지에서도 정확하다.
- **색인** (`src/main/index-db.ts`, `indexer.ts`)
  - 위치는 `.loreweave/index.db`(`node:sqlite`)다.
  - 바뀐 화만 다시 읽는다. 형식이 다르거나 파일이 깨지면 다시 만든다.
  - WAL + `synchronous = NORMAL`로 둔다.
- **화면**
  - 사이드바 검색창(Ctrl+Shift+F)과 결과 목록이 있다. 결과를 누르면 그 줄로 이동해 화면 가운데에 선택해 보여 준다.
  - 중복 id 경고에 [새 id 발급] 버튼을 둔다.

## M2 중에 정한 것 (DECISIONS)

- SQLite는 Electron 내장 `node:sqlite`를 쓴다 (better-sqlite3에서 변경).
- 중복 id는 경고와 버튼으로 처리한다. 앱이 자동으로 파일을 고치지 않는다.
- id가 없는 기존 화는 건드리지 않는다.
- 검색은 부분 문자열 훑기로 충분해서 FTS5는 넣지 않았다. 1000화 검색이 146ms라 기준(200ms) 안이다.

## 진행 중 문제와 교훈

- **첫 색인이 기준을 넘음 (2.24초)**: 화마다 커밋할 때 fsync가 병목이었다. 색인은 다시 만들 수 있는 정보라 WAL + NORMAL로 바꿨고, 0.7초가 됐다.
- **깨진 색인을 지우지 못함**: 열기에 실패한 DB 핸들을 닫지 않고 지우려 해서 Windows에서 `EPERM`이 났다. 단위 테스트가 잡았다.
- **검색 결과로 이동해도 선택이 사라짐**: 새로 연 에디터의 자동 포커스(문서 처음)가 뒤늦게 실행돼 선택을 덮어썼다. 이동할 곳이 있으면 자동 포커스를 끈다.
- **재현하지 못한 실패 1건**: 앱을 켜자마자 검색하는 E2E가 한 번 시간 초과로 실패했다. 바로 앞 테스트의 앱이 색인 파일을 잡고 있었던 것으로 보인다. 다시 돌려도 재현되지 않았다. 색인을 열 수 없을 때는 검색창에 오류 문구가 뜨고, 테스트에는 실패 시 화면 내용을 남기는 진단을 넣었다.
- **PR 운영**: M1의 교훈대로 M2는 처음부터 main 기준으로 하나씩 올렸다. 다음 단계 작업은 로컬 브랜치에 두었다.

## 한계와 다음으로 넘기는 것

- **앱 두 개가 같은 프로젝트를 여는 경우를 막지 않는다.** 색인 파일이 잠겨 두 번째 앱은 검색할 수 없다. 원고는 쓰기 전 해시 비교로 보호된다. 단일 인스턴스 잠금(`requestSingleInstanceLock`)을 검토할 만하다.
- **1000화 첫 색인 2.2초 동안 main 프로세스가 바쁘다.** 파일을 읽을 때마다 양보하므로 화면은 멈추지 않지만, 더 큰 프로젝트에서는 나눠 처리할지 다시 잰다.
- `node:sqlite`는 Node에서 아직 실험 기능 경고가 붙는다. 접근은 한 모듈에 모여 있다.
- 검색은 정확히 같은 글자만 찾는다. 띄어쓰기가 다르거나("김 민수") 조사가 붙은 변형은 따로 찾지 않는다. 필요하면 M3 이후 인물 사전과 함께 다룬다.
- 성능은 빠른 데스크톱 한 대에서만 쟀다.
- 다음 단계는 M3(OpenAI 연결)다. ADR 0001의 B 전략(Fact + 원문 인용)을 쓰려면, 다시 만들 수 없는 AI 결과를 어디에 어떻게 저장할지(색인과 분리, 마이그레이션)를 정해야 한다.
